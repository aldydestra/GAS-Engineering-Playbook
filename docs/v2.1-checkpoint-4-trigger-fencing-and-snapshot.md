# v2.1 Checkpoint 4 — Trigger UID Fencing & Per-Execution SOURCE Snapshot

**Status:** `Unreleased / IN_DEVELOPMENT` · **Date:** 3 November 2026 · **Stable GitHub Release:** `v2.0.0`

## Why this checkpoint

Checkpoint 3 detects SOURCE edits *between* invocations via a pinned SHA-256 seal. Two safety gaps remained:

1. A delayed installable trigger with the **same handler** can still fire *after* its scheduled wake has been replaced; relying only on the cleanup of old trigger objects does not fence a queued event.
2. An operator can edit a mutable Sheet **during** one multi-batch invocation. Each batch previously fetched SOURCE again, potentially mixing rows from different spreadsheet states under one cursor.

The Apps Script event-object documentation states that installable triggers provide `e.triggerUid`; `Trigger.getUniqueId()` identifies a specific installed trigger. We compare those IDs without integer arithmetic. See official references at end.

## Implementation

### A. Event-bound wake validation (engine + demo)

- `GASReliableJobs.checkWakeEvent(config,e)` is a read-only fast-path. Manual invocation omits `e`; installable invocations require `triggerUid` of a safe numeric type or nonempty string.
- `resumeReliableSheetUpsert(e)` rejects a stale/foreign event **before** accessing any SOURCE/TARGET data.
- `GASReliableJobs.run(config, worker, e)` repeats the UID check **under `ScriptLock`** before rescheduling or updating a state property. This protects against another invocation rotating the wake between external check and lock acquisition.
- Status `STALE_TRIGGER_IGNORED` means **no processing, no cursor advance, no new/delete trigger operation**.
- `e.triggerUid` should remain a string if provided as one; unsafe numeric IDs are rejected to prevent lossy comparison. The actual type on a live Google host must still be verified.
- A manual no-event call remains possible for operators. That path is not intended as an authentication or access-control boundary; restrict Apps Script editor permissions appropriately.

### B. Bounded per-invocation SOURCE snapshot

- `gasRJVerifiedSourceSnapshot_()` reads the entire bounded SOURCE once (500-row chunks) and validates the **same pinned SHA-256 chain** as Checkpoint 3.
- Every `gasRJUpsertChunk_` within the same invocation consumes rows from that snapshot rather than re-reading mutable SOURCE. A mid-invocation edit therefore cannot mix new rows into subsequent chunks.
- At the **next invocation** the seal is verified again; if the live SOURCE has changed, job is paused before writing.
- Example limits: **10,000 data rows** and **2,000,000 serialized characters** per snapshot. These are application guardrails, **not** official Google quotas or a hard memory-byte guarantee.
- This prevents within-run row-version mixing but does **not** provide a cross-service transaction or prevent SOURCE edits after the snapshot is captured. Use an immutable staging sheet/row-ID cursor for larger workloads or true snapshot isolation.

### C. Non-mutating operator diagnostic

`inspectReliableSheetUpsertStaging()` reports `jobStatus`, `cursor`, `visibleOwnedWakeCount`, `visibleSameHandlerCount`, and `triggerState`. It does not schedule/delete triggers or modify Sheets. `CHECK_OWNER_OR_REARM` means exactly one visible trigger matching the persisted UID was not found for the **current account**. Apps Script only exposes triggers installed by the calling account; a different account owner may need to inspect its own triggers.

## Staging acceptance procedure (manual, on a disposable spreadsheet)

1. Create staging `SOURCE` and `TARGET` sheets with two-column `record_id | value` headers. Use a *dedicated* Apps Script project and one Google owner account. Populate at least 1,200 unique IDs. **Never run this test on production Sheets.**
2. Paste the development `.gs` files into an Apps Script V8 project; replace `REPLACE_WITH_SPREADSHEET_ID` with the staging spreadsheet ID. Do not put OAuth credentials in source.
3. Invoke `preflightReliableSheetUpsert()` manually and record `PREFLIGHT_PASS`; inspect `inspectReliableSheetUpsertStaging()` with status `NOT_STARTED`.
4. Run `startReliableSheetUpsert()` and record its job status/cursor and `inspectReliableSheetUpsertStaging()` results. Observe time-driven continuation trigger(s) under **the same account** in Apps Script Triggers/Executions.
5. Let scheduled invocations progress; record elapsed wall-clock time and number of execution events. Compare TARGET unique-ID count and values with SOURCE, then run `auditReliableSheetUpsert()` (read-only).
6. For negative testing, **on a separate new job/staging copy**, modify a SOURCE row between invocations. Confirm `RJ_SOURCE_DRIFT`, `PAUSED` and **unchanged cursor**.
7. Under a second disposable job, record a previous wake UID before rotation; call `resumeReliableSheetUpsert({triggerUid:oldUid})` as a local simulation and confirm `STALE_TRIGGER_IGNORED` and unchanged cursor. This manual invocation is **not** proof that an actual delayed trigger event was delivered.
8. To verify trigger owner isolation, inspect from a second account with access to the script, but do not create/delete unowned triggers. Compare reports; treat differences in visibility as expected until verified on host.
9. Keep a sanitized evidence note: run date/time, Apps Script project type (standalone/bound), account type (consumer/Workspace), script version, row count, execution count, statuses, observed `typeof e.triggerUid`, and `NOT_RUN/PASS/FAIL` by scenario. **Do not share tokens, personal emails, spreadsheet IDs or real customer rows.**

## Tests and release gate

Run `node tests/node/test_reliable_jobs.cjs`, Python quality suite, packaging, routing, and stable SHA-256 check. Static/fake results are separate from real Apps Script execution; no release tag is created at this checkpoint.

## Known limits

- The example uses one static job ID and one pair of Sheets, intended for a single operator-owned staging deployment. Cross-account trigger ownership and manual invocation permissions remain platform/ACL concerns.
- `LockService` only serializes operations that use the same script lock. Sheets editors or external APIs can still mutate external data.
- `SpreadsheetApp.flush()` reduces the risk of an uncommitted cache of writes before the checkpoint, but not end-to-end transactional exactly-once semantics. `record_id` upsert must remain idempotent.
- `triggerUid` values may be represented differently in documentation and real events; verify live type before acceptance.
