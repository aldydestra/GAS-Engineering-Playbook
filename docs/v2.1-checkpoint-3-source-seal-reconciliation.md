# v2.1 Development — Checkpoint 3: Source Seal & Read-Only Reconciliation

**2 November 2026 · IN_DEVELOPMENT / Unreleased · Last stable v2.0.0**

## Problem statement

A positional Sheets cursor such as `nextCursor=52` loses its meaning when an operator edits, inserts, deletes, or reorders SOURCE between time-driven invocations. A generic boolean acknowledgement before `FAILED` recovery also says nothing about whether the *committed prefix* in TARGET remains consistent. Both cases can cause incorrect business reporting without a visible error.

## Implemented behavior

1. `startReliableSheetUpsert()` now runs a read-only duplicate-key preflight and computes a deterministic **SHA-256 chained digest** of `SOURCE` `record_id,value` data (max **10,000 data rows**). The digest and row count are stored as a short `ScriptProperties` seal bound to `jobId` *before* starting the engine. The digest itself contains no raw row values.
2. `resumeReliableSheetUpsert()` and `restartPausedSheetUpsert()` re-read the SOURCE data **once per script invocation** and compare with the saved seal. A mismatch raises `RJ_SOURCE_DRIFT` and pauses an active job while preserving its last committed cursor. Only the job-owned trigger is removed. No automatic resealing is allowed for an existing job.
3. `auditReliableSheetUpsert()` checks the committed prefix of SOURCE (`row 2` through `cursor-1`) against TARGET by unique `record_id`, returning aggregate counts for missing, mismatched, duplicate TARGET IDs, and `sourceUnchanged`. It is read-only and does not store row values or identifiers in logs.
4. `recoverFailedSheetUpsertAfterReconciliation(true)` requires explicit operator acknowledgment **and** a passing committed-prefix audit plus a valid seal. It preserves the durable cursor. Never infer that uncommitted in-flight side effects are fully safe from prefix audit alone: inspect those side effects separately before approving.
5. `record_id` is validated as a nonempty string or safe integer. In-memory key maps use null prototypes, so IDs such as `__proto__` and `constructor` do not corrupt the upsert index.

## Usage order (STAGING ONLY)

```javascript
preflightReliableSheetUpsert();          // key/headers, read-only
startReliableSheetUpsert();              // seal + begin + first bounded run
inspectReliableSheetUpsert();            // cursor / status / trigger metadata
auditReliableSheetUpsert();              // read-only check of committed rows
// Normally time-driven trigger resumes automatically:
resumeReliableSheetUpsert();             // manual invocation for controlled staging
pauseReliableSheetUpsert();              // during maintenance
restartPausedSheetUpsert();              // refuses SOURCE drift
// For FAILED only: investigate error and partial uncommitted output first.
auditReliableSheetUpsert();
recoverFailedSheetUpsertAfterReconciliation(true);
```

A new import needs **a new `jobId`**. Never delete or overwrite the old seal/state just to force a restart. Source changes after starting a job require a deliberate new job with a fresh snapshot/dataset and reconciliation of prior target effects.

## Explicit boundaries

- **The seal is a drift detector, not a transaction or permission boundary.** It is computed and checked at invocation boundaries, not on every row write. A source edit during the same execution after verification may still affect the current chunk; production must freeze SOURCE or read from a genuinely immutable snapshot.
- Reading/rehashing all input rows adds approximately `ceil(rows/500)` `getValues()` calls per invocation. 10,000 is a conservative demo cap, **not** a documented Google service quota. For larger inputs use an immutable source snapshot, CDC / keyed cursor, or a stable external data store; do not increase this cap blindly.
- A `ScriptProperties` seal is not cryptographically authenticated against an administrator who can modify the script properties; it is intended to detect accidental input drift, not malicious tampering.
- `auditReliableSheetUpsert()` checks **committed prefix only** and is bounded at 10k SOURCE / 50k TARGET rows. It does not establish correctness of partially written in-flight rows, detect external changes after the audit, or authorize irreversible operations.
- A bad source may be PAUSED, but terminal `COMPLETED`/`FAILED` is not silently reset. In-progress trigger deletion still depends on the executing account's visibility. `ScriptLock` cannot create a cross-service atomic transaction.
- The saved seal uses `JSON.stringify()` of `getValues()` results, including canonical Date serialization; formula results or volatile values can change and intentionally trigger drift. Prefer static values-only SOURCE snapshots.
- No actual Google Apps Script live execution, OAuth, timing, or quota measurements were performed in this checkpoint. Node fakes are **simulated evidence** only.

## Verification / fault injection

| Scenario | Expected behavior |
|---|---|
| SOURCE unchanged across two continuations | Seal PASS, cursor advances, target matches prefix |
| SOURCE value edit / insert / delete / reorder | `RJ_SOURCE_DRIFT`, PAUSED, cursor preserved |
| Existing unrelated trigger shares handler | Survives job-specific pause |
| TARGET committed row missing or value changed | `RECONCILIATION_REQUIRED`, no writes |
| TARGET has duplicate `record_id` | `RECONCILIATION_REQUIRED` |
| Recovery with no explicit acknowledgment | Rejected |
| Recovery with acknowledgment but invalid audit | Rejected |
| SOURCE > 10,000 rows | Fail before job trigger creation |
| Key `__proto__` / `constructor` | Safe keyed upsert; duplicate detection still works |
