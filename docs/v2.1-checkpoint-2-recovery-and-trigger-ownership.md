# v2.1 Development Checkpoint 2 — Trigger Ownership, Replay Safety & Staging Preflight

**Date:** 30 October 2026 · **Status:** `IN_DEVELOPMENT` / `Unreleased` · **Last stable:** `v2.0.0`

## Goal

Reduce the chance of other jobs being damaged by a continuation trigger cleanup, and make the reusable GAS job starter safer before live staging validation. This checkpoint does **not** create a GitHub Release or increase the internal version of any specialist skill.

## Changes (before → after)

| Concern | Previous behavior | Current behavior / boundary |
|---|---|---|
| Trigger ownership | Delete **all** triggers whose handler name matches | Persist only the returned `Trigger.getUniqueId()` in ScriptProperties; delete only the recorded trigger ID visible to the current account |
| Trigger replacement | Delete previous wake before creating the replacement | **Create → persist new UID → delete old**; if persistence fails, delete newly created trigger and leave prior wake intact |
| Job restart | `begin()` could restart an already completed `jobId` | Reject reuse of any existing job state; a logically new run needs a distinct `jobId` |
| Input validation | `maxRunMs` coerced strings or NaN | Require finite integer timing and safe integer cursor/worker counters |
| Staging data | Duplicate IDs checked within the current worker batch only | Read-only `preflightReliableSheetUpsert()` checks **all** SOURCE/TARGET keys up to 50,000 data rows, including duplicates across batches |
| Sheets writes | One `setValues()` for each existing target key | Coalesce updates for contiguous target rows; read only target key column and batch append new keys |
| Stress coverage | Small mock fixtures | Mocked 1,200-row / 12-chunk workload with a replay after commit; still **not** real Google performance evidence |

## Trigger ownership limits

- Source of identity: [Apps Script Trigger.getUniqueId()](https://developers.google.com/apps-script/reference/script/trigger). It is different from the handler function name.
- Trigger visibility: `ScriptApp.getProjectTriggers()` only lists the current user's installable triggers, not another account's. Use **one dedicated trigger owner account** for a given job. Do not share the same public handler across unrelated jobs unless it explicitly dispatches safely by stable job ID.
- Replacing a trigger temporarily requires **one spare quota slot**; quota exhaustion is returned as an error instead of deleting the existing watchdog first. Google currently documents up to 20 triggers per user/script; check the official [quotas](https://developers.google.com/apps-script/guides/services/quotas) before operations.
- Trigger API calls and `PropertiesService` are **not transactional**. Process termination between trigger creation and persisting its ID can leave an orphan trigger. Inspect triggers manually during staging recovery. We never claim absolute one-and-only-one delivery or strict exactly-once effects.
- A time-driven trigger `after(milliseconds)` specifies a **minimum delay**, not exact execution time; no bounded-time completion guarantee.
- A completed state cannot be silently reinitialized. Use a fresh job ID to start a genuinely new import, or deliberately reconcile/retire state offline.

## Source/target safety and scaling

1. Use a dedicated **staging spreadsheet** (`SOURCE` and `TARGET` with `record_id,value`). SOURCE must remain **immutable** for the duration of row-offset checkpoint processing; insert/delete/reorder can still skip or reprocess records. The preflight validates uniqueness **at scan time** only and does **not** freeze the source.
2. Set `GAS_RJ_DEMO_SHEET_ID`, then run `preflightReliableSheetUpsert()` first (read-only). It validates headers, blank/duplicate keys, and returns sourceRows, targetRows and estimatedBatches. Over 50,000 data rows: stop and use an external bounded audit; do not scan arbitrarily large sheets in a trigger.
3. Run `startReliableSheetUpsert()` manually under the dedicated trigger owner. Observe `inspectReliableSheetUpsert()` and target unique `record_id`. Run enough batches to span multiple executions; record trigger UID visibility, authorization and durations.
4. Use `pauseReliableSheetUpsert()` for non-emergency stop. For `FAILED`, reconcile partial sink writes before `recoverFailedSheetUpsertAfterReconciliation()`. Resume from the last committed cursor, not from an assumed last input row.
5. **No irreversible side effects** in this starter without separate provider-side idempotency/reconciliation. The sample uses a Sheet upsert, not payment/email/external POST semantics.

### Suggested live test matrix (manual, staging only)

| Test | Expected observation |
|---|---|
| Two or more clock-trigger continuations | Cursor progresses; at most one managed wake UID per job; completed job leaves no managed trigger |
| Separate unrelated trigger using same handler name | Must remain installed after job pause/completion |
| Revoke script trigger authorization or exhaust trigger quota | Fail closed; unrelated triggers untouched; operator can restore permissions and explicitly resume |
| Artificial exception after `SpreadsheetApp.flush()` | Old cursor replay is idempotent; duplicate count remains zero |
| SOURCE row insertion during run (negative test in a disposable copy) | Hazard documented; do not claim safe resume from row offsets |
| New `jobId` after old job COMPLETED | New job may be started only with a deliberately distinct identifier |
